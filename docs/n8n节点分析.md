# n8n 工作流节点分析与本系统取舍

> 分析来源：`docs/n8n工作流截图/`（2026-09-25 截图，n8n 节点目录）
> 本系统定位：数据表 + AI + 通知 + 审批的办公自动化工具，面向**非技术用户**。
> 结论分三档：✅ 已有等价能力｜🔵 要做（含优先级）｜⚫ 不做（附原因）

---

## 一、节点目录的顶层分类（n8n 的组织方式）

| n8n 分类 | 含义 | 本系统对应 |
|---|---|---|
| AI | 自主代理、总结、文档搜索等 | AI 类（LLM 处理） |
| Action in an app | 几百个第三方 SaaS 应用集成（Google Sheets、Telegram…） | 无（见 §7） |
| Data transformation | 数据处理：过滤、转换、合并 | 数据类 / 逻辑类 |
| Flow | 分支、合并、循环等流程控制 | 逻辑类 |
| Core | 代码、HTTP、Webhook 等基础能力 | 动作类 / 触发器 |
| Human in the loop | 人工审批、等待人工输入 | 人工类（人工审批） |
| Add another trigger | 一个流程挂多个触发器 | ⚫ 不做（一个流程一个触发器，够用且简单） |

## 二、AI 类节点

| 节点 | 作用 | 结论 |
|---|---|---|
| AI Agent | 自主规划并执行动作、可调用外部工具（多步推理 + 工具循环） | ⚫ 不做。超出办公自动化定位，实现重、不可控 |
| Anthropic / Google Gemini / OpenAI / Ollama | 各家模型厂商的专用节点 | ⚫ 不做。本系统「设置 → 模型服务」已支持任意 OpenAI 兼容接口 + Claude，换模型在设置里做，不占节点 |
| Basic LLM Chain | 最简单的"给提示词→出文本"链 | ✅ 已有：LLM 处理节点 |
| Information Extractor | 从文本里按结构化格式提取信息 | ✅ 已有：LLM 处理 + JSON 输出 + 「信息提取」预设 |
| Question and Answer Chain | 基于检索到的文档问答（RAG） | ⚫ 不做。需要向量库/检索基建 |
| Sentiment Analysis | 情感倾向分析 | ✅ 已有：LLM「情感分析」预设 |
| Summarization Chain | 长文本压缩成摘要 | ✅ 已有：LLM「摘要总结」预设 |
| Text Classifier | 把文本分到预设类别 | ✅ 已有：LLM「文本分类」预设 |
| Guardrails | 拦截恶意输入/不当输出（AI 安全护栏） | ⚫ 不做。小企业场景用不上 |
| Embeddings / Vector Stores | 向量嵌入与向量数据库 | ⚫ 不做。同上，无 RAG 基建 |
| AI Templates | AI 场景模板快捷入口 | 🔵 可做（低优先级）：模板市场后续补 AI 场景模板即可，形式已有 |

## 三、Data transformation 数据加工类

| 节点 | 作用 | 结论 |
|---|---|---|
| Code | 运行自定义 JS/Python 代码 | ⚫ 不做。用户不写代码；服务端执行用户代码有安全负担 |
| Date & Time | 日期时间换算（格式化、加减、时区） | 🔵 可做（低优先级）。目前筛选里的相对日期操作符（过去 N 天等）已覆盖大部分场景 |
| Edit Fields (Set) | 增删改记录的字段 | ✅ 已有：新增/更新记录节点的字段赋值 |
| Filter | 按条件删掉列表中的条目 | ✅ 已有：查询节点的筛选条件 |
| Limit | 限制条目数量 | ✅ 已有：查询节点的条数上限 |
| Remove Duplicates | 按字段值去重 | 🔵 可做（中优先级）。实现简单，数据清洗常用 |
| Split Out | 把条目内嵌的列表拆成独立条目 | 🔵 随「逐条处理」二期一起做（见 §4 Loop） |
| Aggregate | 把多个条目的某字段聚成一个列表 | ✅ 已有：汇总统计节点（其 stats/groups 覆盖且更强） |
| Merge | 两路数据流都到达后合并 | ⚫ 不做。模板变量可直接引用任意上游节点，需求已变相覆盖 |
| Summarize | 跨条目求和/计数/最大值等 | ✅ 已有：汇总统计节点 |
| Compression | 压缩/解压文件 | ⚫ 不做。与记录工具无关 |
| Convert to File | JSON 转二进制文件 | ⚫ 不做。导出 Excel 已在数据表功能里 |
| Crypto | 哈希/加解密 | ⚫ 不做 |
| Edit Image | 图片缩放/模糊/加边框文字 | ⚫ 不做。图片处理不是办公自动化主场景 |
| Extract from File | 二进制文件转 JSON（读 Excel/PDF 等） | ✅ 已有：Excel 导入是独立功能模块 |
| HTML / Markdown / XML | 标记语言互转 | ⚫ 不做。通知模板纯文本足够 |
| Rename Keys | 批量改字段名 | ✅ 已有：字段赋值可写新字段 |
| Sort | 排序 | ✅ 已有：查询节点的排序字段 |

## 四、Flow 流程控制类

| 节点 | 作用 | 结论 |
|---|---|---|
| If | true/false 两路分支 | ✅ 已有：条件分支 |
| Switch | 按表达式/规则多路分流 | ✅ 已有：多路分支节点（动态分支出口） |
| Filter | （同数据类） | ✅ 已有 |
| Merge | （同上） | ⚫ 不做 |
| **Loop Over Items（Split in Batches）** | 把列表分批/逐条循环执行后续分支 | ✅ 已有：逐条处理节点（foreach）——「每条」出口接循环体、末尾连回本节点形成回边，「完成」出口接后续；引擎剔除回边后仍按 DAG 校验 |
| Compare Datasets | 比较两路输入的差异 | ⚫ 不做。场景少 |
| Execute Sub-workflow | 调用另一个工作流（模块化复用） | 🔵 可做（中优先级）：跨流程复用一段逻辑（如统一的"通知主管"子流程）。需要引擎支持嵌套执行 |
| Stop and Error | 主动抛错终止流程 | ⚫ 不做。失败处理已有 终止/跳过/重试 三档 |
| Wait | 等待后继续 | ✅ 已有：延迟等待 |

## 七、Action in an app（几百个 SaaS 集成）

截图里这一大类是 n8n 的核心壁垒：几百个海外 SaaS（Airtable、Asana、HubSpot、Notion……）的专用连接器。

**结论：整体不做。** 原因：

1. 全部是海外 SaaS，目标用户用不到；
2. 单个连接器价值低、维护量大；
3. 真需要对接某个系统时，**HTTP 请求节点 + Webhook 触发器**就是通用逃生舱；
4. 国内高频场景（企业微信、钉钉）已用通知通道覆盖。

如果未来有具体对接需求（如金蝶/用友/有赞），按"一个集成 = 一个模板 + HTTP 节点配置"的方式做，不做通用连接器框架。
