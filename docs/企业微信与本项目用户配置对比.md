# 企业微信与本项目用户配置对比

> 核查日期：2026-10-19。项目现状以当前源码为准，企业微信以本文链接的官方资料为依据。本文比较企业内部成员、组织结构和权限配置；不把外部联系人当成内部员工，也不将企业微信智能表格的全部产品能力纳入比较。

## 1. 结论

企业微信围绕“企业通讯录”配置成员，再分别配置组织关系、应用可见范围和管理权限。本项目围绕“账号加入工作空间”配置成员，通过角色控制功能、通过表操作权限与记录范围控制业务数据。

本项目已经具备多租户、部门树、直属上级、租户角色和记录级数据范围，不能再按早期设计文档描述成“只有 admin/vip/user 和整表分享”。当前最值得借鉴企业微信的是成员入职流程、企业内成员资料、组织关系的企业归属，以及按范围委派管理权限的方式。

优先建议：**先把部门、直属上级从全局用户迁入租户成员关系，再完善成员创建/邀请和离职撤权流程，最后按需求接入企业微信登录及通讯录同步。**

## 2. 企业微信的用户如何配置

### 2.1 先建立企业通讯录

通常由管理员在企业管理后台的通讯录中维护部门和成员：先建立部门层级，再添加成员资料、安排所属部门和上级，邀请员工加入。较大企业还可以通过通讯录接口与自己的人员系统衔接。部门以父部门 ID 形成层级关系。[官方：创建部门](https://developer.work.weixin.qq.com/document/path/90205)

从官方成员接口看，成员配置包含以下几类信息：

| 类别 | 典型配置 | 作用 |
|---|---|---|
| 企业内身份 | `userid`、姓名、别名 | `userid` 是企业内唯一的成员账号；姓名用于展示 |
| 联系方式 | 手机、邮箱、座机 | 联系和邀请；创建接口要求手机、邮箱至少提供一项 |
| 组织归属 | `department`、`main_department` | 支持多个所属部门，并指定主部门 |
| 职务和汇报 | `position`、`is_leader_in_dept`、`direct_leader` | 职务、各部门负责人标志、直属上级 |
| 状态 | `enable`、`to_invite` | 控制启用/禁用，以及是否发出使用邀请 |
| 补充资料 | 头像、地址、扩展属性、对外职务 | 员工资料及对外展示 |

以上是接口支持的配置，不代表管理后台每个输入框都必填。当前创建成员接口仅允许通讯录同步助手或第三方通讯录应用调用，不能假设普通自建应用拿到凭证就能创建成员。[官方：创建成员](https://developer.work.weixin.qq.com/document/path/90195)

### 2.2 再配置使用范围与管理范围

需要分别理解这些问题：

| 配置层 | 回答的问题 | 与业务数据的关系 |
|---|---|---|
| 部门、上级 | 员工属于哪里、向谁汇报？ | 提供组织关系，不应直接等同于业务管理员身份 |
| 通讯录查看范围 | 员工能查看哪些同事的信息？ | 管的是人员信息的可见性 |
| 应用可见范围 | 哪些人能使用这个应用？ | 管的是应用入口和使用范围 |
| 管理员权限 | 谁可以管理企业配置、哪些人员或应用？ | 属于管理后台的委派管理 |
| 应用内部权限 | 进入应用后，能看哪些数据、做哪些操作？ | 由具体应用的权限模型决定 |

企业微信应用的可见范围包含人员、部门、标签三个维度。因此可以按销售部门开放某个应用，也可以用标签覆盖跨部门人员。**应用可见并不自动等于拥有应用中所有业务数据的读写权限。**[官方：获取应用](https://developer.work.weixin.qq.com/document/path/90227)

企业微信另有超级管理员、分级管理员的管理机制。具体管理组和可配置项应以实际企业后台为准；本文不将其细化成未经后台验证的菜单操作步骤。官方参考入口：[权限管理](https://open.work.weixin.qq.com/help2/pc/20933)。该帮助页本次未能提取到正文，精确设置项不作为本文已核实结论。

### 2.3 一个直观例子

配置一名销售员工时，先在企业通讯录中建立其成员身份，将其加入华东销售部，设置直属上级；再把销售相关应用开放给该部门。若要让销售经理管理部门人员，还需配置对应管理权限；若要求销售员只能看自己的客户，仍需在客户管理应用内部配置数据权限。

也就是说，“在销售部”“能打开销售应用”“能管理销售部成员”“能看销售客户数据”是不同的配置维度。

## 3. 本项目当前如何配置用户

### 3.1 账号与工作空间

项目已经将登录身份和租户身份拆开：

```text
User：全局登录账号
  ├─ username / password_hash / is_platform_admin
  └─ TenantMember：加入某个工作空间的关系
       ├─ tenant_id + user_id
       ├─ role：在这个空间的角色
       └─ status：invited / active / disabled
```

注册接口创建账号、个人工作空间和对应订阅。企业管理员邀请的是已经注册的用户名；对方接受邀请后，成员状态从 `invited` 转为 `active`。同一账号可以加入多个空间，在不同空间拥有不同角色。请求通过 `X-Tenant-Id` 或 `tenant_id` 选择空间，并实时检查有效成员关系。

依据：[登录注册](../backend/app/routers/auth.py)、[成员管理](../backend/app/routers/members.py)、[租户上下文](../backend/app/utils/context.py)。

### 3.2 当前页面的配置流程

1. 员工先注册账号。
2. 管理员切换到目标工作空间，在“组织与成员”中建立部门树。
3. 在成员页按用户名邀请员工并选择角色；员工接受邀请。
4. 为成员设置所属部门和直属上级。
5. 在角色管理中配置功能权限、表操作权限和数据范围。
6. 个别协作场景再配置用户或用户组分享。

前端邀请对话框排除了 `admin`，管理员身份需在成员列表中调整；后端邀请接口本身仍接受管理员角色。这是当前前后端入口行为的差别，不能将前端限制解释为完整的后端策略。

依据：[组织与成员页面](../frontend/src/views/Members.vue)、[角色页面](../frontend/src/views/RolesManage.vue)、[成员接口](../backend/app/routers/members.py)。

### 3.3 权限已经分为多个层次

| 层次 | 当前实现 | 实际含义 |
|---|---|---|
| 平台管理 | `users.is_platform_admin` | 跨租户运维身份 |
| 空间管理 | `tenant_members.role = admin` | 管理该空间成员和配置 |
| 功能权限 | `Permission`、`RolePermission`、`TenantRolePerm` | 全局角色基础权限，以及租户内覆盖 |
| 表操作权限 | `RoleTablePerm` | 查看、新增、编辑、删除四项 |
| 记录范围 | `RoleTableScope` | 全部、本部门及下级、本人及下属、仅本人 |
| 显式协作 | `TableShare`、`GroupMember` | 向用户或组授予表权限 |
| 商业权益 | 套餐、订阅、entitlement | 功能开关和席位等配额 |

其中，当前表访问解析顺序是：租户管理员 → 表主 → 已接受的显式分享 → 企业/私有化空间的成员默认访问。普通成员默认分支再按角色的表操作配置收窄；没有配置行时，四项操作均默认允许。

记录范围仅在 `feature_data_scope` 开启、且授权来源为普通成员默认访问时过滤。管理员、表主和显式分享不受这层范围过滤。未配置范围时回落为 `all`。这意味着“角色设置仅本人”并不是一个不可被其他授权突破的限制。

依据：[表权限判定](../backend/app/utils/access.py)、[记录范围](../backend/app/services/scope.py)、[数据模型](../backend/app/models.py)。功能权限、配额等检查还有各自调用入口，上述顺序专指表授权解析。

## 4. 逐项对比

| 维度 | 企业微信 | 本项目当前实现 | 差异与影响 |
|---|---|---|---|
| 身份中心 | 企业通讯录成员，企业内 `userid` 唯一 | 全局账号 + 租户成员关系 | 本项目适合个人空间与多企业协作并存 |
| 加入流程 | 创建通讯录成员并邀请，支持通讯录系统接入 | 对方必须先注册，再按用户名邀请并接受 | 企业集中开通人员的操作成本较高 |
| 成员资料 | 姓名、联系方式、职务、扩展资料等 | 账号主要是用户名，成员关系主要是角色与状态 | 企业员工档案较薄，登录名和展示名尚未清晰分开 |
| 部门归属 | 多部门、主部门 | 单部门；部门本身带租户 ID | 单部门可满足小团队，但全局保存归属不适合一人多企业 |
| 直属上级 | 企业内配置直属上级 | `users.manager_id` | 已支持汇报链，但归属仍是全局用户 |
| 部门负责人 | 可配置成员在各部门的负责人标志 | `departments.leader_id` | 项目负责人字段不直接参与数据范围计算 |
| 跨部门分类 | 标签可用于应用可见范围 | 用户组用于分享授权 | 用户组可承接部分协作需求，与标签不是完全等价 |
| 应用入口 | 人员、部门、标签构成应用可见范围 | 主要通过角色功能权限控制 | 未见独立的企业应用可见范围模型 |
| 委派管理 | 有分级管理员机制 | 组织与成员主要要求租户 `admin` | 自定义“部门管理员”角色名称不会自动获得部门成员管理权 |
| 数据访问 | 具体应用另行定义 | 角色 × 表操作 + 记录 owner 范围 | 本项目已直接解决业务表的细粒度访问问题 |
| 人员可见性 | 有通讯录查看权限这一独立配置层 | 用户搜索主要基于好友/同组；成员列表要求管理员 | 目前不是企业通讯录的部门可见规则模型 |
| 禁用/离职 | 成员接口支持启用、禁用，另有删除成员能力 | 有状态字段；当前成员页和接口主要提供邀请、接受、拒绝、移除 | 状态字段存在不等于完整停用/恢复和离职流程已实现 |
| 企业微信连接 | 可作为组织身份来源 | 已有企业微信群机器人消息推送 | 消息推送不等于通讯录同步或企业微信登录 |

企业微信侧成员字段与应用范围分别参见：[创建成员](https://developer.work.weixin.qq.com/document/path/90195)、[获取应用](https://developer.work.weixin.qq.com/document/path/90227)。项目侧以第 3 节链接的源码为依据。

## 5. 当前项目最需要注意的差异

### 5.1 组织关系没有随成员关系隔离

`TenantMember` 已经允许一人加入多个企业，但 `department_id`、`manager_id` 仍保存在 `User` 上。

例如，张三在 A 公司属于销售部，在 B 公司属于顾问部。B 公司管理员修改张三的部门，会覆盖同一个 `users.department_id`；回到 A 公司后，成员输出会因部门不属于 A 公司而显示未分配，按部门计算的数据范围也可能退化为仅本人。移除成员时，当前代码还会清空其全局部门和上级字段，从而影响其他空间的组织配置。

这是代码结构推导出的场景风险，本文没有对生产数据执行复现。建议将组织字段迁到 `tenant_members`，先保留每个租户内单部门、单直属上级即可；只有确有兼任需求时再引入多部门关系表。

### 5.2 角色管理和人员管理没有同样细的范围

当前可以给销售经理配置“本部门及下级”的业务记录范围，但成员列表、邀请、修改组织关系等接口使用 `require_tenant_admin`。因此，“能看部门数据”与“能管理部门员工”没有直接对应关系。

如果企业希望各部门自己维护员工，需要增加独立的管理授权，例如“可邀请成员 + 仅本部门及下级”。只加角色名称、只改前端按钮或直接授予 `admin` 都不能表达这种范围。

### 5.3 显式分享会改变数据范围，离职需处理全部授权来源

当前显式分享优先于普通成员权限，且支持跨租户好友分享。销售员即使角色范围为“仅本人”，收到已接受的表分享后，也可能通过分享访问整表，并按分享开关进行操作。

移除成员会删除成员关系并释放相应席位，但该接口没有同时撤销其表分享、用户组关系或转移名下资源。移除后无法再以该空间有效成员身份访问，并不表示所有资源入口都必然失效：表主、已接受分享等路径仍须分别检查。

建议把“移出空间”和“企业离职”区分成两种业务动作；离职流程应明确处理表所有权、记录负责人、用户组、显式分享及其他资源授权，并给出处理结果。

### 5.4 注释和设计稿不能代替运行逻辑

旧设计文档中“无租户”“无部门”“只有表级分享”等现状描述已经落后于代码；其中默认共享、条件共享规则等设计也不能直接认定为已落地。

另外，`User` 注释写平台超管默认不见租户业务数据，但当前 `get_current_context` 允许平台超管在无成员关系时进入指定租户，并将其视为租户管理员；表授权在匹配上下文时可据此放行。评估权限边界时应以实际代码路径为准。

## 6. 建议的演进顺序

| 优先级 | 建议 | 完成后的效果 |
|---|---|---|
| P0 | 部门、直属上级迁到租户成员关系；调整组织查询和范围计算 | A 企业变更不会覆盖 B 企业组织资料 |
| P0 | 明确企业成员默认表权限、显式分享突破范围和离职撤权规则 | 管理员能准确判断成员实际可见数据 |
| P1 | 成员资料增加企业内姓名、员工编号、职务等；支持邀请未注册者、批量邀请 | 企业可集中配置成员，减少逐个注册再邀请的步骤 |
| P1 | 增加成员停用/恢复，以及资源交接流程 | 人员离职与业务数据留存有明确操作路径 |
| P1 | 增加“管理操作 × 管理范围”的分级管理授权 | 部门管理员只维护自己负责的人员和部门 |
| P2 | 接入企业微信身份与通讯录同步 | 已使用企业微信的客户减少重复维护 |
| 按需 | 多部门兼任、标签、通讯录可见规则 | 支持更复杂的组织协作 |

这些是后续建议，不代表本次已修改业务实现。

## 7. 如果未来接入企业微信，如何对应

建议保留项目自己的账号和权限系统，将企业微信作为可选的登录与组织数据来源。

| 企业微信概念 | 建议映射到项目 | 说明 |
|---|---|---|
| 企业 `CorpID` | 企业连接配置 → `tenant_id` | 明确哪个企业连接对应哪个空间 |
| 成员 `UserID` | 外部身份绑定 → `user_id` / `member_id` | 按企业和接入身份体系保存，不仅凭姓名或手机号自动合并 |
| 部门 ID | 部门映射 → 本地 `Department.id` | 不直接复用外部数值主键 |
| 所属部门、主部门 | 租户成员部门归属 | 初期单部门方案可采用主部门，明确不导入兼任关系的限制 |
| 直属上级 | 租户内成员汇报关系 | 先同步成员，再建立上级关系 |
| 启用/禁用、成员变更 | 租户成员状态和同步事件 | 停用后同步处理项目访问资格；资源交接仍由项目定义 |
| 应用可见范围 | 接入该应用的候选成员范围 | 不直接替代项目表权限和记录范围 |

接入设计应分别处理登录验证、身份绑定、组织同步、业务授权。`User.openid` 只是现有微信相关字段，不能据此认定已经具备企业微信成员绑定。代码中的企业微信 Webhook 用于消息推送，也不能用于识别和登录成员。

同步能力还取决于企业微信应用类型及实际获授权限。特别是创建成员接口已有明确的调用主体限制，应先确定接入模式，再决定项目是只读同步通讯录，还是能向企业微信写回人员信息。[官方：创建成员权限说明](https://developer.work.weixin.qq.com/document/path/90195)
