# 工作流节点规范 v1

> 定位：工作流是本产品的核心引擎。本文档定义节点机制、执行协议、数据模型与扩展约定。
> 设计原则：**通用性来自节点机制，不来自节点数量**。引擎核心不认识任何具体节点类型，全部通过注册表接入。

## 0. 定位与路线图

### 0.1 一句话定位

**"把表格、AI、自动化焊在一起的办公工具"**——用户录数据，AI 加工数据，工作流让数据自己流动。

卖点不是"工作流"本身（通用工作流平台赛道已拥挤：n8n / Dify / Coze / 钉钉宜搭 / 飞书多维表格自动化），而是**现有资产与工作流的化学反应**：n8n 有 400 个节点，但它的节点不认识用户的数据；本产品的节点开箱就活在用户自己的表里。

| 已有模块 | 变成工作流节点后 |
|---|---|
| 数据表（dyn_engine） | 查询/写入/监听变更——工作流跑在用户自己的业务数据上 |
| Excel 导入导出 | 文件进、结果出，办公场景的刚需两端 |
| 拍照识别（vision.py） | OCR / 票据识别节点 |
| 报表引擎 | 定时生成报表 → 推送，一条节点搞定 |
| AI 助手（assistant_engine） | 工作流的自然语言入口 |
| 通知 / 邮件 / 短信 | 触达通道齐全 |
| 记事本 | 结果沉淀为文档 |

### 0.2 三个样板间场景

先做 3 个能演示的场景，比堆 100 个节点有用。三者恰好覆盖产品的三个差异化：**可验证性、人审卡点、成本可视化**。

| 场景 | 流程 | 用到的节点 | 体现的差异化 |
|---|---|---|---|
| **票据管家** | 拍照上传发票 → AI 识别 → 自动入账 → 超预算自动提醒负责人 | record_created → llm（vision）→ create_record → condition → send_message | 可验证（识别结果可回放审计）、成本可视（识别 token 记账） |
| **智能客服台账** | 录入客户反馈 → AI 分类定级 → 高优短信通知 → 每周自动生成处理情况报表 | record_created → llm_transform → condition → send_message(sms) ；schedule → query_records → llm → send_message(email) | 可验证（分级结果进 NodeRun）、成本可视 |
| **审批流** | 任何表的新记录 → 负责人审批（站内通知点通过）→ 通过后自动执行后续动作 | record_created → approval → condition → 后续动作 | 人审卡点（一等公民） |

### 0.3 架构分期

**第一期（返工成本高，必须一次做对）：**
- 节点注册表 + Schema 驱动（§4）——扩展性的根，第一天就这么设计
- 执行异步化：`workflow_jobs` 数据库队列 + worker 轮询领取（§2、§6）。不上 Celery——与 SQLite/MySQL 双兼容现状匹配，自研队列约百行代码
- Run / NodeRun 日志模型（§2）——可观测性与成本可视化的地基，字段一次设计全

**第二期（架构留口子，按需长出来）：**
- 分支的完整形态、失败重试策略、审批节点、数据变更触发（规范中已定义语义，实现可延后）
- **工作流作为 AI 助手的工具** ✅ 已实现：助手新增 `run_workflow` 动作（prompt 注入工作流清单 → align 校验归属 → 卡片确认 → `/assistant/execute` 同步执行 → 跳转轨迹页）

**第三期（生态）：**
- 模板市场 ✅ 已实现（内置版）：`services/workflow/templates.py` 4 个场景模板（低库存预警/反馈分流/收支日报/报销审批），安装时自动建表或复用同名表并重映射 table_id；后续可扩展用户分享模板
- **MCP 暴露** ✅ 已实现：无依赖最小 JSON-RPC 服务（initialize/ping/tools/list/tools/call），`POST /mcp/{token}` 免登录（URL 即凭证），每个启用工作流暴露为 `run_workflow_<id>` 工具；token 在设置页生成/轮换（`app_settings.mcp_tokens`）

### 0.4 to C / to B 的路线取舍

工作流成为核心卖点后，打磨方向取决于目标用户（前 80% 代码相同，后 20% 方向完全不同）：

| 路线 | 优先做 | 暂缓 |
|---|---|---|
| **to C / 小团队** | 模板、AI 生成、移动端体验；节点不求多求"开箱即用" | 复杂权限、审计导出 |
| **to B** | 审批、RBAC 深化、审计日志、私有化部署、稳定性 | 模板市场、移动端打磨 |

> 当前默认按 **to C / 小团队** 推进（与个人/小团队数据工具的产品形态一致）；to B 所需能力（审批、RBAC、审计）在规范中均已预留，转向成本低。

## 1. 核心概念

| 概念 | 说明 |
|---|---|
| **Workflow（工作流）** | 一张流程定义：一个触发器 + 若干节点 + 节点间的连线 |
| **Node（节点）** | 流程中的一个步骤。每个节点有类型（type）、配置（config）、输入、输出 |
| **NodeType（节点类型）** | 节点的"类"，注册到引擎的注册表中。加新能力 = 注册新 NodeType |
| **Run（执行实例）** | 工作流的一次执行。有独立的状态、上下文、日志 |
| **NodeRun（节点执行记录）** | 一次 Run 中某个节点的执行记录：输入快照、输出、状态、耗时、token 消耗 |
| **Context（上下文）** | 节点间传递数据的载体。每个节点的输出以节点 id 为 key 写入，下游节点通过模板语法引用 |

### 与现有模块的关系

- 现有「任务」（TaskRule）是工作流的特例：触发器 + 条件 + 动作 三个节点的预置流程。**保留任务模块 UI 不变**，简单场景继续用任务；复杂场景用工作流。后续可考虑让任务引擎内部走工作流引擎，但 v1 不做迁移。
- 工作流复用现有服务：`dyn_engine`（表查询/写入）、`actions.py`（通知/邮件/短信/webhook）、`llm/gateway`（模型调用）、`scheduler.py`（定时调度）、`notify.py`（站内通知）、RBAC（权限）。

## 2. 数据模型

```python
class Workflow(Base):
    """工作流定义"""
    __tablename__ = "workflows"

    id = Column(Integer, primary_key=True, autoincrement=True)
    name = Column(String(128), nullable=False)
    description = Column(String(500), default="")
    user_id = Column(Integer, ForeignKey("users.id"), index=True)   # 归属用户
    enabled = Column(Boolean, default=False)
    trigger_json = Column(JSON, default=dict)   # 见 §5 触发器
    nodes_json = Column(JSON, default=list)     # [{id, type, name, config, on_error?}]
    edges_json = Column(JSON, default=list)     # [{from, to, branch?}]
    schema_version = Column(Integer, default=1) # 定义格式版本，供未来迁移
    created_at = Column(DateTime, default=datetime.now)
    updated_at = Column(DateTime, default=datetime.now, onupdate=datetime.now)


class WorkflowRun(Base):
    """工作流的一次执行"""
    __tablename__ = "workflow_runs"

    id = Column(Integer, primary_key=True, autoincrement=True)
    workflow_id = Column(Integer, ForeignKey("workflows.id"), index=True, nullable=False)
    trigger = Column(String(16), default="manual")  # schedule / manual / record / webhook / test
    status = Column(String(16), default="pending")  # pending / running / success / failed / waiting / cancelled
    context_json = Column(JSON, default=dict)       # 节点输出汇总 + trigger 数据，审批恢复时用
    tokens_used = Column(Integer, default=0)        # 本次执行消耗的 LLM token 总数
    error = Column(Text)                            # 失败时首条错误信息
    started_at = Column(DateTime, default=datetime.now)
    finished_at = Column(DateTime)


class WorkflowNodeRun(Base):
    """一次 Run 中每个节点的执行记录（审计与成本核算的最小粒度）"""
    __tablename__ = "workflow_node_runs"

    id = Column(Integer, primary_key=True, autoincrement=True)
    run_id = Column(Integer, ForeignKey("workflow_runs.id"), index=True, nullable=False)
    node_id = Column(String(64), nullable=False)    # 对应 nodes_json 中的 id
    node_type = Column(String(32), nullable=False)
    status = Column(String(16), default="pending")  # pending / running / success / failed / skipped / waiting
    input_json = Column(JSON, default=dict)         # 执行前的 config 渲染结果快照（可复现）
    output_json = Column(JSON, default=dict)        # 节点输出
    tokens_used = Column(Integer, default=0)
    duration_ms = Column(Integer, default=0)
    error = Column(Text)
    started_at = Column(DateTime, default=datetime.now)
    finished_at = Column(DateTime)


class WorkflowJob(Base):
    """简易任务队列：worker（调度器内 5s 轮询）领取执行。支撑异步触发、延迟、失败重试、审批恢复。"""
    __tablename__ = "workflow_jobs"

    id = Column(Integer, primary_key=True, autoincrement=True)
    run_id = Column(Integer, ForeignKey("workflow_runs.id"), index=True, nullable=False)
    node_id = Column(String(64))                    # resume/retry 时定位节点；start 为空
    kind = Column(String(16), default="start")      # start（从头执行）/ resume（从节点后继继续）/ retry（重跑该节点）
    execute_after = Column(DateTime, default=datetime.now)  # 延迟执行（delay 节点 / 重试退避）
    attempts = Column(Integer, default=0)
    status = Column(String(16), default="pending")  # pending / running / done / dead
    locked_at = Column(DateTime)
```

> 实现说明：触发数据不放在 job 上——Run 在投递时即创建，`context_json.trigger` 已携带全部触发数据。
> 执行入口分两种：**run_now**（手动/试运行/定时调度，同步执行）与 **enqueue_run**（记录变更/webhook 触发，只投递由 worker 异步执行）。

约束与约定：

- `node_id` 只允许小写字母、数字、下划线（`[a-z0-9_]{1,64}`）——它是模板引用的路径段，也是日志关联键。
- 同一个 Workflow 内 node_id 唯一。
- `context_json` 体积上限建议 256KB，超限节点输出截断并在 output 中标记 `truncated: true`（防止大查询撑爆行记录）。

## 3. Context 协议与模板语法

### 3.1 Context 结构

```json
{
  "trigger": { ... },            // 触发器注入的数据，结构见 §5
  "nodes": {
    "query_1": { "records": [...], "count": 3 },
    "llm_1":   { "text": "...", "data": {...}, "usage": {...} }
  },
  "workflow": { "id": 1, "name": "..." },
  "run":      { "id": 10, "trigger": "schedule" },
  "now": "2026-09-24T09:00:00"
}
```

节点只能**写自己的 key**（`context.nodes.<自己的 node_id>`），读取任意上游输出。不允许节点修改其他节点的输出。

### 3.2 模板语法

沿用现有 `actions.py` 的 `render_template` 单花括号风格，扩展为点路径：

```
{trigger.record.客户名称}
{nodes.query_1.count}
{nodes.query_1.records.0.金额}        // 数组用数字下标
{now}                                 // 当前时间
```

- 解析失败（路径不存在、值为 None）渲染为空字符串，**不抛错**——与现有行为一致。
- JSON 字段（config 中对象/数组类型的值）支持整体模板替换：若某个字段的值**恰好**是一个完整模板表达式且解析结果是 dict/list，则注入原始对象而非字符串。例如 `"record": "{trigger.record}"` 注入整个记录对象。
- 渲染发生在**节点执行前**，渲染结果快照存入 `NodeRun.input_json`，保证可复现、可审计。

## 4. 节点类型接口（核心规范）

### 4.1 NodeType 定义

每种节点类型是一个注册到引擎的类：

```python
# services/workflow/nodes/base.py
from dataclasses import dataclass, field
from typing import Any, Protocol
from sqlalchemy.orm import Session

@dataclass
class NodeResult:
    status: str = "success"        # success / failed / waiting
    output: dict = field(default_factory=dict)   # 写入 context.nodes.<node_id>
    error: str | None = None
    tokens_used: int = 0           # LLM 类节点必须上报

@dataclass
class NodeContext:
    """注入给节点的执行环境。节点不允许直接 import 引擎内部。"""
    db: Session
    workflow: Any                  # Workflow 记录
    run_id: int
    user_id: int
    context: dict                  # 只读视图：读上游输出
    config: dict                   # 已渲染模板后的本节点配置

    # 服务访问入口（引擎统一注入，节点不自行构造）
    # dyn_engine / llm provider / actions / notify 通过这些入口调用，
    # 便于未来做权限校验、成本统计、mock 测试。

class NodeType(Protocol):
    type: str               # 全局唯一标识，如 "query_records"。小写下划线
    name: str               # 显示名，如 "查询记录"
    category: str           # trigger / data / ai / logic / action / human
    description: str        # 一句话说明（给前端卡片和 AI 生成用）
    config_schema: dict     # JSON Schema（draft-07 子集）：配置合法性 + 前端自动渲染表单
    output_schema: dict     # JSON Schema：输出结构（下游引用提示 + AI 生成依据）

    def execute(self, ctx: NodeContext) -> NodeResult: ...
```

### 4.2 注册表

```python
# services/workflow/registry.py
REGISTRY: dict[str, NodeType] = {}

def register(node_cls):
    assert node_cls.type not in REGISTRY, f"节点类型重复注册: {node_cls.type}"
    REGISTRY[node_cls.type] = node_cls
    return node_cls

def get_node_types() -> list[dict]:
    """供 GET /api/workflows/node-types：前端画布与 AI 生成都从这里取。"""
    return [{"type": t.type, "name": t.name, "category": t.category,
             "description": t.description,
             "config_schema": t.config_schema,
             "output_schema": t.output_schema} for t in REGISTRY.values()]
```

**铁律：**

1. 引擎主循环只通过 `REGISTRY[node.type]` 找到实现并调用 `execute`，**不含任何针对具体节点类型的分支逻辑**。
2. 加新节点 = 在 `services/workflow/nodes/` 下加一个文件 + `@register`，引擎、API、前端表单零改动。
3. 未注册的类型在执行时报 `未知节点类型: xxx`，该节点标记 failed，按 `on_error` 策略处理。

### 4.3 config_schema 约定（JSON Schema 子集）

前端（Web 画布 + 小程序）根据 config_schema 自动渲染配置表单，因此只允许以下子集，保证三端都能渲染：

- 类型：`string` / `integer` / `number` / `boolean` / `object` / `array`
- `string` 可用 `format` 提示控件：`textarea`（多行模板）、`template`（带变量选择器）、`table-ref`（数据表选择器）、`field-ref`（字段选择器，需配合 `x-table` 指定来源表）、`provider-ref`（模型供应商选择器）、`date` / `datetime`
- `enum` + `enumNames`（中文显示名）
- `required`、`default`、`minimum` / `maximum`、`minItems` / `maxItems`
- 扩展字段以 `x-` 开头（如 `x-table`、`x-group` 用于表单分组）

不支持：`oneOf` / `anyOf` / `$ref` / 嵌套 `if-then`（条件表单靠前端特判，不进 schema）。

## 5. 触发器规范

`trigger_json` 单数：一个工作流一个触发器。多触发场景拆成多个工作流。

| type | 配置 | trigger 注入 context 的数据 |
|---|---|---|
| `interval` / `cron` | `{type:"interval",minutes:n}` 或 `{type:"cron",expr:"..."}`（与任务模块 schedule_json 同格式，复用 `scheduler.trigger_of`） | `{}` |
| `record_created` | `{table_id}` | `{record: {...}}` |
| `record_updated` | `{table_id, watch_fields?: [field_name]}` | `{record: {...}, old_record: {...}}` |
| `webhook` | `{secret}`（URL 由系统生成） | `{params: {...}}`（query + body 合并） |
| `manual` | `{}` | `{params: {...}}`（手动触发时用户填的参数） |

- 记录变更触发：在 `dyn_engine` 的新增/更新写入点埋 hook，变更后查找订阅该表的 enabled 工作流，投一个 WorkflowJob。**hook 只投递不执行**，保证写入接口响应速度。
- 去重与冷却：v1 工作流级不做冷却（那是任务模块的语义）；有需要的场景由条件节点自行判断。
- webhook 触发必须校验 secret；记录触发与 webhook 触发都要校验工作流归属用户对该表的 RBAC 读权限。

## 6. 执行引擎语义

### 6.1 主循环

```
1. 创建 Run，初始化 context.trigger
2. 找到起始节点（无入边的节点；线性流程通常只有一个）
3. 循环：
   a. 取当前节点 → 渲染 config 模板 → 写 NodeRun(running, input=渲染结果)
   b. 调用 REGISTRY[type].execute(ctx)
   c. 成功：output 写入 context.nodes[node_id]，tokens 累加，按边找下一节点
   d. failed：按节点 on_error 策略（见 §6.3）
   e. waiting：Run 置 waiting，落盘 context，退出循环（等外部恢复）
4. 无后继节点 → Run 置 success
```

- **分支**：`condition` 类节点 output 中约定 `branch: "true" | "false"`，引擎只走 `edges` 中 `branch` 匹配（或无 branch）的出边。普通节点只走无 branch 的出边。
- **并发**：v1 单线程顺序执行，一个节点多个出边时按边定义顺序逐个执行（广度优先）。并行执行不在 v1 范围。
- **循环**：v1 不支持回边，保存时校验图必须为 DAG。

### 6.2 暂停与恢复（审批等 human 节点）

1. 节点返回 `NodeResult(status="waiting", output={...})`
2. 引擎：NodeRun 置 waiting → Run 置 waiting → context 落盘 → 返回
3. 外部动作（用户点"通过"）调用恢复 API → 补写该 NodeRun 的 output（审批结果）→ 投 WorkflowJob(run_id, node_id=下一节点)
4. worker 从 context 恢复现场继续执行

### 6.3 错误处理

节点级 `on_error`（可选，默认 `stop`）：

```json
{"policy": "stop"}                                  // 默认：Run 失败终止
{"policy": "continue"}                              // 标记 failed，继续走无 branch 出边
{"policy": "retry", "max_attempts": 3, "backoff_seconds": 60}   // 指数退避重试
```

- 重试通过 WorkflowJob 的 `execute_after` 实现：`execute_after = now + backoff * 2^attempts`。
- 超过 max_attempts 降级为 stop。
- 任何异常都落 NodeRun.error 和 Run.error（取首条），与现有 `execute_rule` 的日志习惯一致。

### 6.4 成本与可观测性

- LLM 类节点**必须**在 NodeResult 中上报 `tokens_used`（prompt + completion 合计）。
- 引擎累加到 Run.tokens_used；前端在工作流详情页展示"近 30 天消耗 X token ≈ ¥Y"（单价从模型供应商配置的扩展字段读取，v1 可只做 token 数）。
- 每次执行的完整轨迹（每个节点的输入/输出/耗时）可从 NodeRun 完整回放——这是"可验证性"差异化的数据基础。

## 7. 首批节点清单（v1）

### data · query_records — 查询记录

```json
{
  "table_id": {"type": "integer", "format": "table-ref"},
  "filters": {"type": "object", "description": "{logic: AND|OR, rules:[{field,op,value}]}，与 pyquery.match_filters 操作符一致"},
  "limit": {"type": "integer", "default": 100, "maximum": 500},
  "order_by": {"type": "string"}, "order_desc": {"type": "boolean", "default": true}
}
```
输出：`{records: [...], count: n}`。操作符沿用现有结构化条件的集合（eq/ne/gt/gte/lt/lte/contains/is_empty 等，以 `pyquery.py` 实现为准）。

### data · create_record / update_record — 写入记录

```json
{
  "table_id": {"type": "integer", "format": "table-ref"},
  "field_mapping": {"type": "object", "description": "{field_name: 模板表达式}，值支持整体对象注入"},
  "match_filters": {"type": "object", "description": "仅 update_record：定位记录的条件"}
}
```
输出：`{record: {...}}`。写入必须经过 dyn_engine 的校验与 RBAC 写权限检查。

### ai · llm_transform — LLM 处理

```json
{
  "prompt": {"type": "string", "format": "template"},
  "system": {"type": "string", "format": "textarea"},
  "provider_id": {"type": "integer", "format": "provider-ref", "description": "缺省用默认供应商"},
  "output_format": {"type": "string", "enum": ["text", "json"], "default": "text"},
  "max_tokens_hint": {"type": "integer", "description": "成本控制提示，非硬限制"}
}
```
输出：`{text, data?, usage: {prompt_tokens, completion_tokens}}`。`output_format=json` 时用现有 `extract_json` 解析，解析失败视为节点 failed（可配 retry）。底层走 `llm/gateway.get_default_provider`，**需要给 gateway 补 usage 返回**（当前只有 text 返回）。

### logic · condition — 条件分支

```json
{
  "record": {"type": "string", "format": "template", "description": "整体对象注入，如 {trigger.record}"},
  "logic": {"type": "string", "enum": ["AND", "OR"], "default": "AND"},
  "rules": {"type": "array", "items": {"type": "object", "description": "{field, op, value}"}}
}
```
输出：`{matched: true|false, branch: "true"|"false"}`。求值复用 `pyquery.match_filters`，与任务模块语义完全一致。

### action · notify / email / sms / webhook — 触达

config 直接复用现有 `action_json` 约定：`{type, template, recipients: {type: fixed|field, value|field}, webhook_url?}`。引擎层把四种动作做成一个 `send_message` 节点（type 作 enum），避免节点类型爆炸。输出：`{sent: n, recipients: [...]}`。

### action · http_request — HTTP 请求（通用逃生舱）

```json
{
  "method": {"type": "string", "enum": ["GET", "POST", "PUT", "DELETE"], "default": "POST"},
  "url": {"type": "string", "format": "template"},
  "headers": {"type": "object"}, "body": {"type": "object"},
  "timeout_seconds": {"type": "integer", "default": 30, "maximum": 120}
}
```
输出：`{status, body}`（body 尝试 JSON 解析，失败则给 text）。
**安全**：目标 URL 走管理员配置的域名白名单（AppSetting），默认禁止访问内网网段（10.x/172.16.x/192.168.x/169.254.x），防 SSRF。

### human · approval — 人工审批（差异化节点）

```json
{
  "title": {"type": "string", "format": "template"},
  "detail_template": {"type": "string", "format": "template"},
  "approver_user_ids": {"type": "array", "items": {"type": "integer"}, "description": "可审批人，空 = 工作流归属人"}
}
```
执行时创建站内通知（复用 `notify.py`），返回 `status="waiting"`。审批人点击通过/驳回后引擎恢复执行。输出：`{approved: true|false, comment: "...", approver_id: n}`。驳回默认按无 branch 出边继续（由条件节点决定后续走向）。

### logic · delay — 延迟（v1 可选）

`{minutes: n}` → 投一个 `execute_after = now + n 分钟` 的 WorkflowJob，Run 置 waiting。

## 8. 前端与 AI 生成协议

- **节点目录**：`GET /api/workflows/node-types` 返回注册表全量 schema。Web 画布（Vue Flow）据此渲染节点面板；拖入节点后按 config_schema 动态渲染配置表单（与 DynamicForm 同一思路）。
- **AI 生成**：`POST /api/workflows/ai-assist`（实现：`services/workflow/ai_assist.py`）。把节点目录（type/name/description/config_schema/output_schema）+ 用户自有表结构喂给 LLM，要求输出 `{trigger, nodes, edges}`。生成后先经 `align_workflow_definition` 清洗（未知节点类型/无效配置项/无权限表丢弃并记入 notes），再由服务端校验：
  1. 每个 node.type 在注册表中存在；
  2. config 通过 config_schema 校验（模板字符串字段跳过类型校验）；
  3. 图为 DAG 且连通、只有一个起始节点。
- **试运行**：`POST /api/workflows/{id}/test-run`，与现有任务"试运行"体验一致，返回完整 NodeRun 轨迹供前端逐步展示。

## 9. 扩展指南：新增一个节点类型

1. 在 `backend/app/services/workflow/nodes/` 新建 `my_node.py`
2. 实现 NodeType：定义 `type / name / category / description / config_schema / output_schema`，实现 `execute(ctx) -> NodeResult`
3. `@register` 注册，并在 `nodes/__init__.py` import
4. 写一个最小测试：构造 NodeContext，断言 output 符合 output_schema
5. 前端表单、AI 生成、节点目录 API **自动获得**该节点，无需任何改动

需要引擎级新能力时（如新触发方式、新的错误策略），先改本文档并升 `schema_version`，再改引擎。

## 10. 明确不做（v1 边界）

- 循环 / 回边 / 子流程 / 并行分支
- 节点级权限隔离（v1 节点全部以工作流归属用户身份执行）
- 表达式语言（只有 §3.2 的模板路径，不支持算术/函数）
- 第三方 SaaS 预制集成（用 http_request 节点顶，热门需求再沉淀为专属节点）
- 任务（TaskRule）模块迁移（保持双轨，工作流稳定后再评估）
