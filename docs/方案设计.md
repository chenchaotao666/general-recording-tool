# 通用数据记录工具 — 方案设计

## 1. 产品定位

一个"Excel 驱动的轻量级数据管理系统"：

1. 用户上传 Excel → 大模型自动分析表格结构和数据语义
2. 用户确认结构后 → 自动创建数据库表并导入数据
3. 自动为这张表生成增删改查（CRUD）界面
4. 新增/编辑时支持上传图片，大模型识别图片内容自动填入表单（需用户确认）
5. 任务引擎：用户针对数据配置条件规则，触发自动提醒（短信/站内通知等）

核心理念：**元数据驱动**。表结构、表单、列表、校验规则全部由元数据描述，前端动态渲染，后端动态执行，不写死任何业务表。

---

## 2. 技术选型

| 层 | 选型 | 说明 |
|---|---|---|
| 后端 | Python 3.11 + FastAPI + SQLAlchemy 2.x | 异步 API，动态建表/查询靠 SQLAlchemy Core |
| 前端 | Vue 3 + Vite + Element Plus + Pinia | 表单/表格组件成熟，适合动态渲染 |
| 数据库 | MySQL 8.0 | 单机/局域网够用；业务表 + 元数据表同库 |
| Excel 解析 | openpyxl / pandas | 读取 sheet、表头、样例数据 |
| 任务调度 | APScheduler | 定时扫描任务规则，进程内运行，部署简单 |
| LLM 接入 | 抽象 Provider 接口（可切换） | DeepSeek / 通义千问(Qwen-VL) / Claude / OpenAI |
| 短信通道 | 抽象接口，内置阿里云短信实现 | 可扩展邮件、企业微信 webhook |
| 部署 | Docker Compose（app + mysql）或直接 python + 前端静态文件 | 小团队单机部署 |

## 4. 核心流程设计

### 4.1 Excel 导入 → 建表（导入向导，4 步）

```
上传文件 → AI分析 → 用户确认/调整 → 建表并导入
```

**Step 1 上传解析**
- 接收 `.xlsx/.xls/.csv`，用 openpyxl 读取
- 提取：sheet 列表、每个 sheet 的表头行（自动探测，可能不在第一行）、前 20 行样例数据、总行数
- 处理合并单元格、多级表头、空行等常见脏数据

**Step 2 AI 结构分析**
- 将"表头 + 脱敏后的样例数据（前 10 行）"发给 LLM，要求返回 JSON：
```json
{
  "table_name_suggestion": "客户跟进记录",
  "columns": [
    {
      "source_header": "客户姓名",
      "field_name": "customer_name",
      "label": "客户姓名",
      "data_type": "varchar",
      "length": 64,
      "nullable": false,
      "widget": "input",
      "comment": "客户姓名",
      "confidence": 0.95
    },
    {
      "source_header": "下次跟进日期",
      "field_name": "next_follow_date",
      "label": "下次跟进日期",
      "data_type": "date",
      "widget": "date-picker",
      "confidence": 0.9
    }
  ],
  "notes": "第2行为表头，'备注'列数据多为空"
}
```
- 类型推断规则（LLM + 本地统计双重校验）：
  - 扫描样例数据实际值（日期格式、纯数字、手机号正则、枚举值占比）
  - LLM 语义判断（"到期时间"→ date，即使数据是字符串）
  - 两者冲突时以数据为准，并在 `notes` 中提示用户
- 前端展示分析结果卡片：每个字段的类型、控件、置信度，低置信度字段高亮

**Step 3 用户确认/调整**
- 用户可修改：表名、字段名、字段类型、是否必填、控件类型、删除字段、调顺序
- 这一步是**必经环节**，AI 只给建议，不直接落库

**Step 4 建表导入**
- 生成 DDL：`CREATE TABLE dyn_xxx (id BIGINT AUTO_INCREMENT PRIMARY KEY, ...字段, created_at, updated_at)`，业务表统一加 `dyn_` 前缀与元数据表隔离
- 批量写入：pandas/SQLAlchemy bulk insert，每批 500 行，事务包裹
- 导入报告：成功 N 行、跳过 M 行（类型转换失败记录原始值和原因），失败行可下载
- 同时写入元数据（见 §5）

### 4.2 动态 CRUD 界面

前端完全由元数据驱动，不需要为每张表写代码：

- **列表页**：按元数据生成 el-table 列（label、类型格式化、是否显示）；自动生成分页、排序、按字段类型的筛选器（文本模糊、日期范围、枚举下拉、数值区间）
- **新增/编辑弹窗**：按 `widget` 渲染表单控件（input / textarea / number / date-picker / select / switch / image-upload），按 `validation` 生成校验规则
- **后端动态接口**：通用路由 `/api/dyn/{table_id}/records`，运行时根据表 id 从元数据加载字段定义，用 SQLAlchemy `Table` 反射动态拼 SQL，不做 ORM 模型（业务表是动态创建的，没有静态模型）
- 权限与安全：所有 SQL 字段名来自服务端元数据而非用户输入，杜绝注入；操作记审计日志

### 4.3 图片识别自动填表

```
表单中点"拍照/上传图片" → 调多模态 LLM → 返回字段JSON → 差异预览 → 用户确认 → 填入表单
```

- 入口：动态表单顶部"智能识别"按钮（上传图片或拍照，支持多张）
- 后端将图片 + 当前表字段元数据（label、类型、已有值）发给多模态模型（Qwen-VL / Claude / GPT-4o 任选）：

```
你正在帮用户填写一张"{表名}"表单。表单字段如下：
[{field_name, label, data_type, 当前值}]
请识别图片内容，抽取能对应到这些字段的信息，返回 JSON：
{ "customer_name": "张三", "next_follow_date": "2026-10-01", ... }
规则：
- 只返回能确认的字段，不确定的不要猜
- 日期统一 YYYY-MM-DD
- 编辑场景：图片信息与当前值冲突时，放入 "conflicts" 字段说明
```

- 前端做**差异对比视图**：字段名 | 当前值 | 识别值（新增场景当前值为空），逐字段勾选是否采用，用户确认后才写入表单
- 每次识别留痕（图片、原始返回、用户采纳了哪些字段），便于追溯

### 4.4 任务引擎（条件提醒）

**规则模型**：一条任务规则 = 目标表 + 条件组 + 触发时机 + 动作

```json
{
  "name": "超过1个月未跟进提醒",
  "table_id": 3,
  "enabled": true,
  "condition": {
    "logic": "AND",
    "rules": [
      {"field": "next_follow_date", "op": "date_older_than", "value": "30d"},
      {"field": "status", "op": "eq", "value": "进行中"}
    ]
  },
  "schedule": {"type": "cron", "expr": "0 9 * * *"},
  "action": {
    "type": "sms",
    "template": "客户【{customer_name}】已超30天未跟进，计划跟进日期 {next_follow_date}",
    "recipients": {"type": "field", "field": "owner_phone"}
  },
  "dedup": {"window_days": 7}
}
```

- **条件配置 UI**：针对选定表的字段，按类型给操作符（eq/ne/gt/lt/contains/in/日期早于X天/晚于X天/为空），支持 AND/OR 组合。操作符映射为 SQL where 片段（服务端白名单拼接，不执行用户原始 SQL）
- **执行**：APScheduler 按 cron 扫描规则 → 动态拼 SELECT 找出命中记录 → 逐条执行动作
- **动作类型**（插件化，第一期实现）：短信、站内通知、邮件、webhook
- **防重复轰炸**：`task_trigger_log` 记录 (rule_id, record_id, last_fired_at)，同一记录同一规则在 `window_days` 内不重复触发
- **执行日志**：每次扫描记录命中数、发送成功/失败明细，前端可查

## 5. 数据库设计（元数据表）

```sql
-- 业务表注册
meta_table (
  id, name 物理表名(dyn_xxx), label 显示名,
  source_file 来源excel, status, created_at, updated_at
)

-- 字段定义（动态表单/列表/校验的唯一依据）
meta_field (
  id, table_id, field_name, label,
  data_type  -- varchar/int/decimal/date/datetime/text/bool
  length, nullable, default_value,
  widget     -- input/textarea/number/date-picker/select/image...
  options    -- JSON: 枚举项、校验规则、列表是否显示、排序权重
  sort_order
)

-- 导入批次记录
import_batch (id, table_id, file_name, total, success, failed, fail_detail_file, created_by, created_at)

-- 任务规则
task_rule (id, table_id, name, enabled, condition_json, schedule_json, action_json, dedup_json, created_at)

-- 任务触发去重
task_trigger_log (id, rule_id, record_id, fired_at)

-- 任务执行日志
task_run_log (id, rule_id, run_at, matched_count, sent_count, fail_count, detail_json)

-- 图片识别留痕
vision_log (id, table_id, record_id, image_path, raw_response, adopted_fields, created_by, created_at)

-- 审计
audit_log (id, user, action, table_id, record_id, before_json, after_json, created_at)

-- LLM 配置（可多家，运行时选择）
llm_provider (id, name, type, base_url, api_key(加密存储), model, vision_model, is_default, enabled)
```

业务表：`dyn_*`，统一含 `id / created_at / updated_at`。

## 6. LLM 网关设计（可切换的关键）

统一接口：

```python
class LLMProvider(Protocol):
    def analyze_excel(self, headers, sample_rows) -> TableSchemaSuggestion: ...
    def recognize_form(self, images: list[bytes], fields: list[FieldMeta], current: dict) -> dict: ...
    def complete(self, prompt: str) -> str: ...  # 通用兜底
```

- 内置实现：`OpenAICompatible`（覆盖 DeepSeek/通义/OpenAI 及一切兼容接口）+ `ClaudeProvider`
- 关键工程点：
  1. **结构化输出兜底**：优先用各家 JSON mode / tool use；不支持则 prompt 约束 + 本地 JSON 解析 + 失败重试 1 次（把解析错误回喂让模型修正）
  2. **Prompt 模板集中管理**（`prompts/` 目录），便于调优
  3. **数据脱敏**：发样例数据前对手机号/身份证做掩码
  4. **成本控制**：Excel 分析只发表头 + 前 10 行；图片压缩到 1024px 内再发
  5. 调用超时、限流、失败降级提示

```

POST /api/excel/analyze             触发 LLM 结构分析
POST /api/tables                    确认结构 → 建表 + 导入
GET  /api/tables                    已建表列表
PUT  /api/tables/{id}/fields        调整字段元数据（影响表单/列表）

GET    /api/dyn/{tid}/records       列表（分页/筛选/排序）
POST   /api/dyn/{tid}/records       新增
GET/PUT/DELETE /api/dyn/{tid}/records/{rid}

POST /api/vision/recognize          图片识别（multipart，返回建议JSON）
GET  /api/vision/logs

GET/POST/PUT/DELETE /api/tasks      任务规则 CRUD
POST /api/tasks/{id}/test           试运行（只返回命中记录，不发通知）
GET  /api/tasks/{id}/runs           执行日志

GET/POST /api/settings/llm          LLM 供应商配置 + 连通性测试
```

## 8. 关键风险与对策

| 风险 | 对策 |
|---|---|
| LLM 分析结构不准 | 必经人工确认环节；置信度标注；本地统计校验兜底 |
| Excel 格式千奇百怪（合并单元格、多级表头） | 解析阶段预处理 + 让用户在向导中手动指定表头行/数据起始行 |
| 动态 SQL 注入 | 字段名一律取自服务端元数据，参数化查询，操作符白名单 |
| 任务重复发短信骚扰 | 触发去重表 + 冷却窗口 + 每条规则可设每日上限 |
| 短信/LLM 密钥泄露 | 密钥加密存储（Fernet），日志脱敏 |
| 业务表字段变更导致数据丢失 | 字段修改只允许"安全的"操作（改名/加列）；删列/改类型需二次确认并备份表 |
| 图片识别错误写入脏数据 | 识别结果永不自动落库，必须用户确认；留痕可回溯 |

## 9. 迭代计划（建议）

**M1 核心链路（2~3 周）**
Excel 上传解析 → LLM 结构分析 → 确认建表导入 → 动态列表/表单 CRUD

**M2 智能录入（1~2 周）**
图片识别填表（新增场景）、差异确认 UI、LLM 供应商管理

**M3 任务引擎（2 周）**
规则配置 UI、APScheduler 执行、站内通知 + 短信、试运行与日志

**M4 完善（持续）**
编辑场景图片识别、字段变更迁移、审计界面、数据导出回 Excel、用户权限
