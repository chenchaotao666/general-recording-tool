# 用户与权限体系设计（对标销售易CRM 的裁剪方案）

> 状态：分析稿 ｜ 2026-10-09（2026-10-10 修订：部门树/职级由"暂缓"调整为"引入"；
> 补 tenant_members 语义、匿名外部填写者判定、企业过期态、私有化 license 配额口径）
> 参考：`docs/用户与权限管理/*.png`（销售易CRM 系统设置截图）
> 结论先行：销售易的体系是"**功能权限（职能）与数据权限（角色）两层分离 + 组织树定范围 +
> 规则化共享 + 权限可反查**"。本项目引入其**分层模型、组织树（轻量单树）、默认共享、
> 共享规则、权限反查**五个理念，都能在现有模型上渐进演进。

## 0. 前置决策：租户模型与套餐层（先于一切权限设计）

本系统走 **SaaS 多租户（个人版/企业版）+ 私有化部署（=单租户实例，同一套代码）**双形态。
所有业务数据必须挂在租户下，**租户隔离是权限判定的第一行**，先于角色、范围、分享。

```
tenant（租户/工作空间）
 ├─ type = personal（个人版，1 席）| enterprise（企业版，N 席）
 ├─ subscription → plan（套餐）→ plan_entitlements（配额 + 功能开关）
 └─ 成员、数据表、用户组、分享、共享规则……全部带 tenant_id

tenant_members（成员关系，权限语义的核心载体）
 └─ tenant_id + user_id + role + status(invited/active/disabled)

完整判定链：
套餐(功能开关/配额) ∩ 租户边界 ∩ 职能(功能权限) ∩ 角色(对象×操作×范围)
                    ∩ 默认共享(OWD) ∪ 共享规则 ∪ 手动分享
```

- **一人可属多租户**（工作空间切换）；**role 下沉到 membership**：同一个人在 A 租户是 admin、
  在 B 租户是普通成员。`users` 表不再承载业务 role，只留平台超管标记（is_platform_admin）；
  现有 `users.role` 的业务语义迁移到 `tenant_members.role`（见 §4.7 vip 迁移）。
- **邀请成员 = tenant_members 增员**：触发 max_seats 校验（entitlement 收口），
  status 从 invited 接受后转 active；席位计数 = 该租户 active+invited 成员数。
- 私有化部署 = 只有一个租户的实例，代码不分叉；**私有化 = 功能全开 + 配额按合同**：
  feature_* 全开（旗舰权益），但 max_seats 等配额按 license 合同档（≤50/≤200/不限）
  写入 plan_entitlements——按用户规模阶梯收费（见定价文档 §5）因此可落地。
- **个人版可一键升级企业版**（定价文档 §3）：tenant.type personal→enterprise，
  数据不动（同一 tenant_id 下全部数据随迁），解锁协作子系统入口、开放成员邀请；
  原 owner 成为企业租户的第一个 admin membership。
- `users.role` 中的 `vip` 是付费等级概念，需迁移为套餐（plan）；role 只保留权限语义
  （admin/manager/user 等），见 §4.7。
- 配额（max_tables 等）从"角色权限项"上移为"套餐权益"；角色的 permissions 只管功能与操作。
- 个人版租户下，所有多人协作权限子系统（角色矩阵/OWD/共享规则/诊断）整体隐藏——
  产品上是两个皮肤，代码上是一套。

详细分档与定价见 `docs/定价与套餐设计.md`。

## 1. 销售易CRM 权限模型解读（截图归纳）

| 模块 | 作用 | 关键设计 |
|---|---|---|
| **角色管理** | **数据权限**：角色 = 「业务对象 × 操作 × 数据范围」矩阵 | 矩阵列：查询/修改/删除/转移；值：全部/部门范围/本人等。角色回答"能看多少数据" |
| **职能管理** | **功能权限**：职能 = 功能开关包（前台/后台功能） | 职能有 API 名称，可分配用户。职能回答"能用哪些功能" |
| **资源权限管理** | 资源组 + 管控开关 | 可分别启用"职能资源管控 / 角色资源管控 / 审批流资源管控"——数据权限是可开关的子系统 |
| **部门/用户管理** | 组织树 + 用户归属 | 用户挂部门，有职位/职级/直属上级/角色/职能 |
| **用户职级** | 职级树 | 支撑"部门及内部下级"这类自上而下的数据范围 |
| **公共组** | 跨部门用户集合 | 成员可含用户/部门/嵌套公共组；支持"基于角色自动共享" |
| **流程用户组** | 工作流/审批专用组 | 与协作组分开 |
| **默认共享设置** | **OWD**（组织级默认）：每个业务对象的"内部用户默认访问权限" | 专用（私有）/ 公用只读 / 公用读写——没有显式共享时的兜底 |
| **共享规则** | **规则化自动共享** | 「基于数据负责人 / 基于条件」把对象数据共享给 部门及下级/公共组，权限只读/读写，支持"重新计算" |
| **数据权限查询** | **权限反查** | 对象+数据+用户+操作 → 为什么有/没有权限（共享原因/方式/链路详情） |
| **字段权限查询** | 字段级权限（FLS）排查 | 按职能维度定位敏感字段的读写分配 |

其精髓可概括为一条权限判定链：

```
用户能否操作 = 职能(功能开关) ∩ 角色(对象×操作×范围) ∩ 默认共享(OWD) ∪ 共享规则 ∪ 手动分享
```

## 2. 本项目现状盘点

| 已有 | 模型 | 相当于销售易的 |
|---|---|---|
| 用户角色（admin/vip/user） | `users.role` 单角色 | 无（只有单层） |
| 功能权限 | `permissions`（code）+ `role_permissions`（布尔/数值：share、create_physical_table、max_tables） | **职能**（雏形） |
| 表级分享 | `table_shares`（用户/用户组 × can_view/create/edit/delete） | 手动分享 |
| 用户组 | `groups` + `group_members`（可加好友） | 公共组（雏形） |
| 好友 | `friendships` | 无对应 |
| 组织（部门/职级/上级） | 无 | 部门树 / 用户职级（§4.6 引入） |
| **租户 / 套餐** | 无（全局单池，`vip` 混在 role 里） | 无对应（需新建，见 §0 / §4.7） |

现状的特征：**功能权限有雏形；数据权限只有"表级手动分享"这一层，没有"范围"概念**
（一张表要么全表可见、要么不可见，没有"只能看自己的记录"）。

## 3. 差距分析：借鉴什么、暂缓什么

### 值得引入（按价值排序）

1. **数据范围（角色矩阵）** ⭐ 最核心差距
   销售易矩阵的本质：`对象 × 操作 × 范围`。落到本项目：`数据表 × 操作（查询/新建/修改/删除）× 范围（全部 / 本人及下属 / 仅本人）`。
   典型场景：客户表全员录入，但销售员只能看自己建的记录，经理能看全组——目前做不到，只能整表分享或不分享。

2. **功能权限与数据权限分层**
   现有 role 一身二任（admin/vip/user 既管功能又隐含数据）。演进为：**角色（功能权限包）+ 数据角色（范围矩阵）**，或更轻的方案：保留 role 管功能，新增"数据范围"作为角色上的附加维度（见 §4 推荐）。

3. **默认共享（OWD）**
   表级"默认访问权限"：私有（仅 owner+显式分享）/ 全员只读 / 全员可编辑。目前每张表默认"仅自己 + admin + 分享"，新业务表想全员可见必须手动逐个分享——OWD 一行配置即可解决。

4. **共享规则（基于条件的自动共享）**
   现有分享是"整表 × 到人/组"。规则化共享是"满足条件的记录 × 到人/组"，如"把华东区客户共享给华东销售组（只读）"。记录级共享的入口，同时覆盖"转交/重新计算"运维需求。

5. **权限反查**
   "他为什么能看到这条记录 / 为什么不能编辑这张表"——协作一多就是高频问题。销售易的反查页给出共享原因+链路。本项目可在表设置里加一个"权限诊断"：输入用户 → 输出该用户对该表的合成权限及来源（owner/OWD/分享/组分享/规则/admin）。

6. **部门树 / 职级（轻量组织体系）**（2026-10-10 决策：由暂缓调整为引入）
   团队到一定规模后"按部门管数据"是刚需——销售、客服、财务各看各的，经理看本部门，
   只靠 manager 链表达不了"部门"这个天然边界。采用**轻量实现**：单棵部门树 + 用户单归属，
   不搞多维组织/虚线汇报/多部门兼任；职级做薄（名称+高低序号），只为"本部门及内部下级"
   这类自上而下范围服务。详见 §4.6。

### 建议暂缓（过重或不适配）

- **字段级权限（FLS）**：字段读写矩阵实现重、UI 复杂。可后置，先用"字段显隐"（已有的列配置思路）承接非敏感场景。
- **资源组/流程用户组等细分容器**：现有"用户组"可统一承接，不拆。
- **API 名称/导入导出**：内部工具不需要。

## 4. 适配设计（推荐方案）

### 4.1 权限分层模型

```
用户
 ├─ 角色 role（沿用现有，功能权限包：permissions × role_permissions）   ← 功能层
 └─ 数据角色 data_role（新增，范围矩阵：表 × 操作 × 数据范围）           ← 数据层

单表有效权限 = 租户边界 ∩ 套餐功能开关 ∩ 功能层允许 ∩ 数据层允许（范围过滤）
             ∩ 表 OWD ∪ 表分享 ∪ 共享规则
admin 恒为全部（租户内）；平台超管仅运维用途，默认不可见租户业务数据。
```

为避免两层角色给管理员带来的理解负担，**推荐轻量合并**：不新增"数据角色"实体，
而是在现有 `roles` 上增加"数据范围"维度——每个角色对每个数据表/或全局默认，
配置一个范围值。角色列表页从"权限项勾选"扩展为"权限项 + 数据范围矩阵"两栏。

### 4.2 数据范围模型（核心）

```python
class RoleTableScope(Base):        # 角色 × 表 的数据范围
    __tablename__ = "role_table_scopes"
    id = Column(Integer, primary_key=True)
    role_id = Column(Integer, ForeignKey("roles.id"), index=True)
    table_id = Column(Integer, ForeignKey("meta_tables.id"), index=True)  # NULL=全局默认
    scope = Column(String(16), default="all")   # all / dept_tree（本部门及下级）/ subtree（本人及下属）/ own（仅本人）
    rank_limit = Column(Boolean, default=False)  # 仅 dept_tree 生效：再叠加"职级不高于我"（§4.6，P2）
```

- `scope=all`：现状不变（该角色成员看全表）；
- `scope=dept_tree`：`owner 所属部门 ∈ 我的部门及其全部下级部门`（部门树见 §4.6）；
- `scope=own`：列表/详情/导出/报表均过滤 `owner_id = me`（记录补 `owner_id`，默认=创建人，存量回填）；
- `scope=subtree`：`owner_id ∈ me + 我的下属（沿 users.manager_id 下钻）`；
- 范围按 **owner_id 而非 created_by** 过滤：记录会换主人（离职、重新分配），配套补一个
  "记录转移"操作（单条/批量改 owner_id）；created_by 只留作审计信息，不参与权限；
- 表分享（table_shares）**优先于**范围：被显式分享的表/记录不受范围限制（分享 = 显式开闸，与销售易一致）。
  注意写透：**分享/共享规则都会击穿数据范围**，scope 只约束"默认池子"，不是硬约束。

判定顺序（ dyn_engine.list_records / get_record 统一收口）：
```
if 记录.tenant_id != 当前租户: 拒绝（第一行，所有查询强制带租户过滤）
if 套餐未开通数据范围功能（feature_data_scope=0）: scope 视为 all（低档行为=现状）
if user.role == 'admin': 全量
elif 有该表分享记录（本人或所属组）: 按分享权限
elif 角色对该表 scope == all（或默认 all）: 全量
elif scope == dept_tree: owner.department_id ∈ 我的部门子树（rank_limit 时叠加职级过滤）
elif scope == subtree: owner_id ∈ 下属集合
else (own): owner_id = 本人
```

**匿名外部填写者（公开表单/工单）**——定价文档 §2.3 已定"外部填写者免费、不占席位"，
他们不进入上面的判定链，走独立的免登录写入通道：

- 公开链接带表单 token → 定位到表与租户，**仅允许 INSERT** 到开启了公开提交的表，
  不能读、不能改、不能删；
- 不经过角色/范围/分享判定（无登录身份），但必须过租户配额闸：表单提交计入该租户
  max_rows（总条数口径），超限同样禁止新增（定价文档 §8 校验点含"表单提交"）；
- 匿名提交的记录 `owner_id` = 该公开表单的归口成员（开启分享时指定，默认=表单创建者），
  使 scope=own/subtree/dept_tree 下提交进来的数据有明确归属、有人可见；
  表单停用或归口人离职时批量改挂（随 §5 P4 离职流程一并处理）。

### 4.3 表级默认共享（OWD）

`meta_tables` 加一列：

```python
default_access = Column(String(16), default="private")   # private / read / edit
```

- `private`：现状（owner + admin + 显式分享）；
- `read`：全员可查（只读）；
- `edit`：全员可读写（不含删表/改结构）。
判定在 §4.2 的"分享记录"之前短路：OWD≠private 时直接给对应权限（仍受功能层/范围层约束）。

### 4.4 共享规则（记录级自动共享）

```python
class ShareRule(Base):
    __tablename__ = share_rules = Column(Integer, ForeignKey("meta_tables.id"), index=True)
    name = Column(String(64))
    filters_json = Column(JSON)          # 与列表筛选同格式（复用 _parse_filters）
    target_user_id = Column(Integer, ForeignKey("users.id"))
    target_group_id = Column(Integer, ForeignKey("groups.id"))
    access = Column(String(8), default="read")   # read / edit
    enabled = Column(Boolean, default=True)
```

- 判定时在分享检查后追加："命中某启用规则"→ 赋予 read/edit；
- 规则按条件实时求值（不做物化快照，免去"重新计算"运维负担——数据量小，实时足够）；
- UI：表设置 → 共享 → 两个页签「指定人/组」（现有）+「规则共享」（新增）。

### 4.5 权限反查（权限诊断）

- 后端：`GET /tables/{id}/perm-diagnose?user_id=` → 返回合成结果：
  `{ can_view, can_create, can_edit, can_delete, scope, sources: ["owner","role:subtree","share#12","rule#3","owd:read","admin"] }`；
- 支持传入 `record_id` 做记录级反查："他为什么**看不到这条记录**"比表级更高频——输出该记录
  被哪一环过滤掉（不在 owner 范围 / 未命中分享 / 未命中规则）；
- 前端：表设置 → 权限诊断，选用户即出"合成权限 + 每条的来源"，管理员排查一步到位。

### 4.6 组织体系：部门树 + 职级 + 直属上级（轻量实现）

```python
class Department(Base):            # 部门树（租户内单树）
    __tablename__ = "departments"
    id = Column(Integer, primary_key=True)
    tenant_id = Column(Integer, ForeignKey("tenants.id"), index=True)
    name = Column(String(64))
    parent_id = Column(Integer, ForeignKey("departments.id"))   # NULL=根部门
    leader_id = Column(Integer, ForeignKey("users.id"))         # 部门负责人（信息展示/审批用，不参与范围判定）
    sort = Column(Integer, default=0)
    enabled = Column(Boolean, default=True)

class JobLevel(Base):              # 职级（薄：名称+高低序号）
    __tablename__ = "job_levels"
    id = Column(Integer, primary_key=True)
    tenant_id = Column(Integer, ForeignKey("tenants.id"), index=True)
    name = Column(String(32))        # 如 P5 / M2 / 实习生
    level_no = Column(Integer)       # 数值越小职级越高，用于"职级不高于我"比较

# users 表加三列：
department_id = Column(Integer, ForeignKey("departments.id"))   # 单归属
manager_id    = Column(Integer, ForeignKey("users.id"))         # 直属上级（保留，见下）
job_level_id  = Column(Integer, ForeignKey("job_levels.id"))
```

设计约束（刻意做轻）：

- **单树单归属**：一个用户只属于一个部门，不支持多维组织、虚线汇报、多部门兼任——
  这些在销售易里都重，中小团队用不上；真出现兼任需求，用"用户组 + 分享"承接。
- **`scope=dept_tree` 判定**：取我的部门子树 id 集合（parent 链递归，限 10 层防环，
  用户量少可缓存 5min）→ 过滤 `owner.department_id ∈ 集合`。
  未分配部门的用户（department_id=NULL）在该范围下只看得到自己。
- **`rank_limit`（P2 后置）**：dept_tree 上叠加"记录 owner 的职级不高于我"
  （`owner.job_level.level_no >= 我的 level_no`；任一方未设职级则视为不满足，退化为只看自己），
  对应销售易"部门及内部下级"。
- **`manager_id` 保留的原因**：① 没建部门的小团队/个人版升级初期，subtree 开箱即用；
  ② 汇报线 ≠ 部门线（矩阵团队、跨部门带人）；③ 后续审批流/工作流的"提交给直属上级"。
- **部门运维规则**：移动部门时校验不成环；删除部门前要求成员已迁出（或批量置 NULL）；
  停用部门后其成员视同未分配。
- **UI**：系统设置 → 组织与成员：左侧部门树（增删改/拖拽排序/设负责人），
  右侧成员列表（按部门过滤，批量改部门/上级/职级）；用户管理页加"所属部门/直属上级/职级"三列。

### 4.7 套餐权益与功能分档（plan_entitlements）

付费等级（plan）与权限角色（role）分离：plan 决定"能用多少/哪些功能"，role 决定"能看哪些数据"。

```python
plans                # code / name / audience(individual|enterprise|private) / price_monthly / price_yearly
plan_entitlements    # plan_id + key + value：
                     #   配额类 max_tables / max_rows / max_storage_mb / max_seats / min_seats
                     #   功能类 feature_data_scope / feature_owd / feature_share_rules /
                     #        feature_perm_diagnose / feature_field_perm / feature_audit /
                     #        feature_automation / feature_api
                     #   保留类 trash_retention_days / audit_retention_days
subscriptions        # tenant_id + plan_id + seats + status(trial/active/grace/expired) + expires_at
usage_counters       # tenant_id + table_count / row_count / storage_bytes / seat_count
                     # （写入路径维护缓存 + 定时全量校准，避免每单 count 全库）
```

- **校验收口于 entitlement 模块（单点）**：建表→max_tables；写入→max_rows；上传→max_storage_mb；
  邀请成员→max_seats；进角色矩阵/OWD/共享规则/诊断/审计→feature_*（前端隐藏 + 后端 403 双重）。
- **套餐未含某功能时，对应权限层按全开处理**（如 feature_data_scope=0 → scope 恒为 all）：
  低档用户行为 = 现状，高档只是"多了可配置的约束"，保证分档不影响存量逻辑。
  ⚠️ 此规则**仅适用于在档用户**，不适用于过期/降级路径（见下条）。
- **过期 ≠ 放开约束（企业过期态，2026-10-10 决策）**：企业版 expired 后**不落回个人免费档**，
  而是进入独立的"企业过期态"——全员只读 + 可导出，scope/OWD/共享规则等权限配置全部
  保留不删，续费即恢复原状。实现上：过期态只是在 active 判定链前加一道只读闸，
  **scope 范围判定继续生效**——绝不能出现"欠费后经理突然能看全公司数据"的反向放大。
  grace 宽限期内行为与 active 一致（每日提醒，见定价文档 §6）。
- **max_rows 为工作区总条数口径**（定价文档 §2.1），另设单表技术软上限（如 50 万条）防失控——
  软上限是工程保护，不进价格页、不做分档。
- **vip 迁移**：存量 `role=vip` 用户 → 创建个人租户 + 订阅对应套餐，role 落回 user；
  `role_permissions` 中的配额类项（max_tables 等）删除，由 plan_entitlements 承接。
- 分档与定价详情见 `docs/定价与套餐设计.md`。

## 5. 分期路线

**P0：商业化地基（先于一切权限增强——没有它无法售卖）**
- 租户模型：tenants / tenant_members（含 role 迁移：`users.role` 的业务语义下沉到
  `tenant_members.role`，users 只留平台超管标记），所有业务表加 `tenant_id`，
  dyn_engine 查询强制带租户过滤
- 套餐层：plans / plan_entitlements / subscriptions / usage_counters + entitlement 校验收口
- vip 迁移（role 拆 plan）、记录补 `owner_id`（默认=created_by，为范围过滤与记录转移做准备）
- 订阅状态机（trial/active/grace/expired）与超限/到期行为（见定价文档 docs\定价与套餐设计.md）
- 审计日志（轻量 audit_logs：操作人+对象+前后值）——企业版几乎必答，地基期一并建表

**P1：数据范围 + 组织树（企业标准版付费功能，feature_data_scope 控制）**
- `role_table_scopes` + `departments` + `users.department_id/manager_id` + 记录转移操作（单条/批量改 owner_id）
- 组织与成员页：部门树管理 + 成员挂部门/上级
- dyn_engine 查询/详情/导出/打印统一按 §4.2 判定收口（含 dept_tree）
- 角色管理页加"数据范围"配置（全局默认 + 按表覆盖）；预设角色模板：管理员/经理/员工 = all/dept_tree/own

**P2：OWD + 职级 + 权限诊断（企业标准版/旗舰版）**
- `meta_tables.default_access` + 表设置 UI + 判定短路（edit 档明确：含改、不含删记录）
- `job_levels` + `users.job_level_id` + `role_table_scopes.rank_limit`（"本部门及内部下级"）
- 权限诊断接口与页面（含 record_id 记录级反查）

**P3：共享规则（企业旗舰版）**
- share_rules 表 + 表设置「规则共享」+ 判定并入
- 报表/工作流取数口径同步（报表数据集也走同一判定）

**P4（可选）**
- 字段级权限（敏感字段只读/隐藏）
- 离职/停用流程：用户停用后的分享回收、下属 manager 改挂、部门成员批量迁移、名下记录 owner 批量转移

## 6. 风险与注意点

- **租户隔离是第一优先级**：任何查询漏带 tenant 过滤 = 越权事故。在 dyn_engine/ORM 层
  强制注入租户条件（如全局 query hook），而非依赖各 router 自觉；上线前做跨租户访问的自动化测试。
- **取数口径必须单点收口**：列表/详情/导出/打印/报表/关联选择/首页卡片都经过 dyn_engine，
  范围过滤只改一处（list_records + get_record + record_count + 报表数据集的取数路径），
  切忌散落到各 router。打印即变相导出，必须走同一判定。
- **存量兼容**：默认 `scope=all` + `default_access=private` + 套餐全开（私有化）→ 行为与现状
  完全一致，平滑上线。
- **订阅状态机与数据安全**：到期/降级只限制"新增"，绝不删数据；宽限期内每日提醒
  （见定价文档 docs\定价与套餐设计.md）。
- **降级安全（2026-10-10 决策）**：到期/降级绝不出现"数据可见性反而放大"。企业过期态 =
  全员只读 + scope/OWD/规则配置保留 + 范围判定继续生效，续费即恢复（§4.7）；
  "功能未开通按全开"仅适用于在档低档用户，不适用于过期/降级路径。
  个人版降级同理：超限数据只读保留，不删。
- **性能**：subtree 下钻每请求一次（用户量少，可缓存 5min）；share_rules 实时求值复用现有
  filters→SQL 机制，单表规则数预期 <10；usage_counters 用缓存计数 + 定时校准。
- **前端一致性**：范围过滤是"看不见记录"，不等于按钮置灰——新建/编辑按钮仍按功能层 +
  分享权限控制，避免"列表空了但还能新建"的困惑（新建是允许的，只是建完只能看自己的）。
  套餐未含的功能入口整体隐藏（而非置灰），并留"升级可用"提示作为转化入口。
