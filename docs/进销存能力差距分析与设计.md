## 三、差距功能设计

### 3.1【P0】子表 / 主从单据模型 —— ✅ 已实现（V1 嵌入式，2026-09-30）

**V1 已落地的方案（嵌入式 + 弹窗编辑）**：
- 新字段类型 `subform`：明细行作为**主表记录的一个 JSON 字段**整体存取（json 模式存 records.data；physical 模式存 Text 列，与 image 字段同套路），**主从一体保存天然原子**——不需要 `_op: add/update/delete` 协议，不存在孤儿行，删单据连带删明细免费。
- 列结构定义在 `options.columns`：`[{field_name, label, data_type, nullable, widget, options}]`，列级支持关联选择、行内公式、合计回填（见 3.2/3.4）；不允许嵌套子表。
- 表单：`DynamicForm` 渲染 `SubformField` 控件 = **只读明细表格（含合计行）+「添加明细」弹窗**；行编辑弹窗复用 DynamicForm，行内关联带出/公式自动生效。
- 配置入口：表结构抽屉 → 字段「配置」按钮（`FieldOptionsDialog`），subform 列定义可视化编辑。
- 代码落点：`typemap.py`（类型+逐格校验）、`dyn_engine.apply_computed`、`SubformField.vue`、`FieldOptionsDialog.vue`。

**P1 演进路径（跨单据聚合需要时）：给 subform 加存储模式开关**：
```
subform 存储模式：嵌入（默认，V1 现状）/ 独立明细表
```
- 独立模式：明细拆写到 `dyn_*` 明细物理表（挂 parent_id），读时组装回数组——**前端表单、行弹窗、保存协议（主记录带明细数组）一行不改**，只是后端存取层分流。
- 原设想的 `table_kind: detail` + `_op` 协议被嵌入式取代；行内编辑（截图 5 的键盘动线）留作 V2 体验增强，元数据/协议与 V1 完全兼容。
- 触发条件：做 3.7 主从合并明细查询 / 3.8 库存台账时落地（明细须可被 SQL 聚合）。

### 3.2【P0】关联字段（lookup）与联动回填 —— ✅ 已实现（2026-09-30）

- 实现形态：新控件 `relation-picker`（而非新 data_type，存储类型保持 varchar/int 不变），配置在 `options.relation`：`{table_id, value_field, label_field, carry_fields: [{from, to}]}`。
- **带回映射 `carry_fields`**：选中目标记录后按映射回填本表字段——选供应商后自动填名称/地址/联系人/电话；快照语义，回填后字段可再手改。
- 前端：`RelationPicker.vue`（el-select 远程搜索，复用现有列表 API，无需新后端端点）；选中后 `carry` 事件携带整行供 DynamicForm 回填。弹窗选记录形态暂缺（V2 补）。
- 子表列同样支持（行内"选产品带出规格/单价"）。
- 建表/改结构时服务端校验关联配置合法性（目标表/字段存在、映射两端存在），见 `meta_service.validate_field_options`。
- 待办：报表数据集的 join 逻辑复用 relation 元数据，避免两套关联定义。

### 3.3【P0】自动编号字段 —— ✅ 已实现（2026-09-30）

- 新字段类型 `serial`：规则模板 `前缀 + {YYYY}/{YY}/{MM}/{DD} + 流水占位`，流水占位居 `{0000}`（0 的个数=位数）或 `{SEQ}`（默认 4 位），如 `PO{YYYY}{MM}{DD}-{0000}`；留空默认 `{YYYY}{MM}{DD}{0000}`。
- 服务端在插入时按规则+计数器表（`serial_counters`，按 表×字段×周期 一行）发号：UPDATE 行锁自增，首行 INSERT 撞唯一键走 SAVEPOINT 重试，并发不重号。
- 重置周期：`never / daily / monthly`；`allow_manual` 允许手改（手工值不占流水）；**更新时编号不可变**（服务端剥离）；不允许手改时提交值被强制覆盖。
- 配置入口：字段「配置」对话框（规则模板/重置周期/允许手改）；建表时校验模板必须含流水占位。
- 代码落点：`dyn_engine.apply_serials/_next_seq`（json/physical 双模式接入）、`models.SerialCounter`。冒烟：`backend/smoke_serial.py`。
- 已知边界：跳号策略（删除记录不回填号码）= 默认跳号，与主流进销存一致；Excel 导入的存量行保留导入值，不重新发号。

### 3.4【P0】字段级公式（表单内实时计算）—— ✅ 已实现（2026-09-30）

- 实现形态：不新增字段类型，任意字段配 `options.formula`（表达式字符串，如 `qty * price`）即为公式字段。
- **两个求值时机**（均已落地）：
  1. 前端实时：`utils/formula.js` 自研求值器（递归下降，语义与后端 expr.py 对齐：null 传播、除零→null、iff/coalesce/round 等函数白名单、`[字段名]` 括号引用），DynamicForm 内 watch 多遍求值（支持公式引用公式）；
  2. 服务端兜底：`dyn_engine.apply_computed` 保存时重算落库（**公式字段忽略客户端提交值，服务端权威**，防篡改、报表可直接取列）。json/physical 双模式均已接入。
- **合计回填**：子表列配 `options.sum_to: 主表字段名`（如明细金额合计→"合计金额"），前端实时 + 服务端保存时聚合写回；明细表格自带合计行。
- 建表/改结构时校验公式语法与字段引用存在性；保存时配置错误静默降级为 null（不阻断业务录入）。
- 截图 5 的"金额计算公式=数量×单价×折扣"即落在字段定义上的公式字符串，已支持。

### 3.5【P0】单据状态机 + 审核/作废

- 单据类型配置 `status_field + 状态定义列表`：每个状态声明 名称/颜色/是否锁定编辑/允许的操作（审核→锁定、作废→置灰、反审核→解锁）。
- **状态自动流转规则**：`当 X 事件发生时 → 状态改为 Y`，直接编译成一条系统内置工作流（复用 workflow 引擎，不自造轮子）——截图 5 的"出货后改进行中、交货完成改已完成"即两条规则。
- **已超期**：交货日期 < 今天 且状态=未完成 → 查询时动态判定（report/expr 已能算），不落库。
- 状态徽标在单据页大字号显示（截图 2 红色"未打印"），打印后自动翻转"未打印→已打印"。
- 审核动作可挂现有 approval 审批节点；作废要求权限点 + 审计留痕（审计日志已有）。

### 3.6【P0】打印 / 预览 / 打印模板

- 打印模板设计器：单据头字段 + 明细表格 + 页脚（制单人/日期/公司信息）的拖拽排版，HTML 模板 + CSS @page，浏览器打印或后端渲染 PDF。
- 模板绑定单据类型，可多套（送货单/对账单版式不同）；支持自定义变量（单号、合计大写金额等）。
- "预览/打印"按钮进单据工具条；打印事件触发状态翻转（见 3.5）。

### 3.7【P0】主从合并明细查询视图

- 前置依赖：嵌入式明细无法被 SQL 聚合，需先落地 3.1 的「独立明细表存储模式」。
- 新视图类型 `detail_query`：以子表行为行、主表字段平铺展开（截图 3 形态），列可配、支持服务端排序分页、底部合计行、导出。
- **衍生列**：已交数量/未交数量 = 关联单据聚合差值。实现：视图配置 `derived_columns`，表达式里提供 `sum_where(表, 条件)` 聚合函数（expr.py 扩展，SQL 侧编译为相关子查询）。
- 快捷过滤 chips：视图可配置"预设筛选组"（显示全部/未完成/进行中/已完成/已超期 单选切换）——本质是命名的 filter 预设。
- 底部"单据列表 / 单据详细资料"双页签 = 主表视图 / 明细视图切换。

### 3.8【P1】库存台账（进销存的"存"）

- 平台级**流水+余量**模式，而非硬编码库存模块：
  - 新增字段类型 `stock_delta`（或更通用的"记账字段"）：单据审核生效时，按明细行向**台账表**追加出入库流水（仓库×产品×数量正负）；
  - **余量表** = 台账的物化汇总（产品×仓库 → 现存数量/金额），由系统维护，开单界面可显示当前库存。
- 配置化声明：`采购入仓单.审核 → 台账 +数量；采购退货单.审核 → 台账 −数量`——用现有工作流引擎也能拼，但做成"单据类型的库存影响配置"更傻瓜化。
- 多仓库 = 仓库基础资料表 + 台账维度列，天然支持。
- 低库存预警：模板市场已有工作流模板，直接复用。

### 3.9【P1】单据引入（转换生成）

- 单据类型间配置"转换映射"：采购订单 → 采购入仓单（头字段映射 + 明细行映射 + 默认只引入未交数量>0 的行）。
- 单据工具条"引入"按钮：弹窗选源单（可多选合并）→ 生成目标单草稿。
- 引入同时写回源单的"已交数量"累计依据（供 3.7 衍生列使用）。
- 底层可用工作流 create_record 实现，UI 做成原生动作。

### 3.10【P1】批量操作 + 工作台/多标签

- 列表多选列 + 批量删除/批量审核/批量导出/批量修改字段。
- **多标签页容器**：路由切换改为 tab 容器（keep-alive），标签可关闭。
- **工作台首页**：磁贴式快捷入口（绑定菜单项/查询视图/报表），可由报表仪表盘充当统计区；菜单支持分组（进货管理/销售管理/仓库管理/财务管理…）。

## 六、设计原则（保持"通用"不被进销存绑架）

1. **不为进销存写死任何业务表**——所有能力（子表、关联、编号、公式、状态机、台账）都是元数据驱动的平台特性，进销存只是第一个大客户。
2. **能复用引擎就不造新引擎**：状态流转→工作流；统计→报表数据集；公式→expr.py；关联→数据集 join 元数据统一。
3. **配置即产品**：截图 5 的参数设置证明"每个单据类型一套参数"就是低代码的正确粒度，平台功能全部按"单据类型可配"设计。
4. **P0 先做纵切**：用"采购订单"一张单打通全链路（建模→开单→打印→查询→统计），再横向铺开其余单据类型。
